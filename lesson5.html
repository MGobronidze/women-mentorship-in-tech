Display, Background, ტექსტი, ფონტები და Figma

წინა გაკვეთილში ვისწავლეთ, როგორ „ითვლის" ბრაუზერი ელემენტის ზომას. ახლა ვნახოთ, როგორ განლაგდება ეს ყუთები ერთმანეთთან, როგორ ვსტილავთ ფონსა და ტექსტს, საიდან ვიღებთ ქართულ და ლათინურ ვებ-ფონტებს, და როგორ ვკითხულობთ ზუსტ დიზაინის მნიშვნელობებს Figma-დან, რომ ისინი კოდში გადავიტანოთ.

1. display: block / inline / inline-block / none

display თვისება განსაზღვრავს, როგორ „იქცევა" ელემენტი გვერდზე — იკავებს თუ არა მთელ სიგანეს, დგება თუ არა ახალ ხაზზე, აქვს თუ არა width/height.

  • block — იკავებს მთელ ხელმისაწვდომ სიგანეს, ყოველთვის იწყება ახალი ხაზიდან (მაგ. <div>, <p>, <h1>).
  • inline — იკავებს მხოლოდ საჭირო სივრცეს, არ იწყება ახალი ხაზიდან, width/height არ მოქმედებს (მაგ. <span>, <a>).
  • inline-block — „ჰიბრიდი": არ იწყება ახალი ხაზიდან (ისევე როგორც inline), მაგრამ width/height/margin მოქმედებს (ისევე როგორც block).
  • none — ელემენტი სრულად ქრება გვერდიდან, თითქოს საერთოდ არ არსებობდეს.
.block-el    { display: block; }
.inline-el   { display: inline; }
.hybrid-el   { display: inline-block; width: 120px; }
.hidden-el   { display: none; } /* არ ჩანს, საერთოდ არ იკავებს სივრცეს */

2. CSS Background

ფონის დასაყენებლად რამდენიმე თვისება გვაქვს, რომლებიც შესაძლებელია ცალ-ცალკე ან ერთიანი background shorthand-ით ჩავწეროთ: 

.hero {
  background-color: #EAE6D9;
  background-image: url("bg.jpg");
  background-size: cover;        /* ფონის სურათი ფარავს მთელ არეს */
  background-position: center;
  background-repeat: no-repeat;
}

/* ან shorthand ჩანაწერით: */
.card {
  background: #FFFFFF url("texture.png") no-repeat center / cover;
}

3. ტექსტის ფორმატირება: fonts, spacing, alignment

ტიპოგრაფია ერთ-ერთი ყველაზე მნიშვნელოვანი დიზაინის ინსტრუმენტია. ძირითადი თვისებებია:

.article {
  font-family: "Noto Sans Georgian", sans-serif;  /* შრიფტების ჯაჭვი, fallback-ებით */
  font-size: 16px;
  font-weight: 700;          /* სისქე: 400 ჩვეულებრივი, 700 გამუქებული */
  line-height: 1.6;          /* ხაზებს შორის მანძილი — კითხვადობისთვის */
  letter-spacing: 0.02em;    /* ასოებს შორის მანძილი */
  text-align: center;        /* left | right | center | justify */
  text-transform: uppercase; /* ავტომატური დიდი ასოები */
  text-decoration: underline;
}

line-height უნდა იყოს ერთეულის გარეშე რიცხვი (მაგ. 1.6), რადგან ის მაშინ პროპორციულად თვლის font-size-ის მიხედვით — ეს კარგი პრაქტიკაა responsive დიზაინისთვის.

4. ქართული და ლათინური ფონტები ვებში

font-family-ში ფონტის სახელის ჩაწერა საკმარისი არ არის — ეს ფონტი ჯერ „მოსატანია" ბრაუზერისთვის, თუ ის მომხმარებლის მოწყობილობაზე უკვე დაყენებული არ არის. ორი ყველაზე გავრცელებული წყაროა Google Fonts (ლათინური და ასევე ქართული Unicode-ფონტებისთვის) და web-fonts.ge (ტრადიციული ქართული ვებ-ფონტების სპეციალიზებული კატალოგი).

Google Fonts — fonts.google.com

Google Fonts არის უფასო, ღიაკოდიანი ფონტების უდიდესი ბიბლიოთეკა — ათასობით ლათინური ფონტის გარდა, მასში შედის ქართული Unicode-ის (Mkhedruli) მხარდამჭერი ოჯახებიც, მაგ. Noto Sans Georgian და Noto Serif Georgian — ზუსტად ეს ფონტებია გამოყენებული ამ კურსის საიტზეც (გადახედე ნებისმიერი გვერდის <head>-ს).

გამოყენების ნაბიჯები: საიტზე ირჩევ ფონტს → წონებს (weights) → იღებ მზა embed კოდს:

<!-- 1. <head>-ში: preconnect აჩქარებს დაკავშირებას Google-ის სერვერთან -->
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

<!-- 2. თავად ფონტი — რომელი ოჯახი, რომელი წონები (wght) -->
<link href="https://fonts.googleapis.com/css2?family=Noto+Sans+Georgian:wght@400;700&display=swap"
      rel="stylesheet">
/* 3. CSS-ში — ფონტის სახელი ზუსტად ისე, როგორც Google Fonts-ის საიტზეა მითითებული */
body {
  font-family: "Noto Sans Georgian", sans-serif;
}

display=swap პარამეტრი (URL-ში) გადაითარგმნება font-display: swap-ად — ის უზრუნველყოფს, რომ ტექსტი ჩანდეს fallback ფონტით მაშინვე, ხოლო როცა კონკრეტული ფონტი ჩაიტვირთება — გლუვად „გადაერთოს" მასზე (ცარიელი, უხილავი ტექსტის ნაცვლად ჩატვირთვისას).

web-fonts.ge — ქართული ვებ-ფონტების კატალოგი

web-fonts.ge არის ქართული პროექტი, რომელიც აერთიანებს 120+-ზე მეტ, ტრადიციულ ქართულ ფონტს (BPG ოჯახი და სხვ.) — ბევრი მათგანი Google Fonts-ზე საერთოდ არ მოიძებნება. გამოსადეგია, როცა დიზაინი (მაგ. Figma-დან) კონკრეტულ, კლასიკურ ქართულ ტიპოგრაფიულ სტილს მოითხოვს.

თითოეული ფონტის გვერდზე (მაგ. BPG Nateli) მოცემულია რამდენიმე გზა მის დასაკავშირებლად — უმარტივესი CDN-ითაა:

<!-- <head>-ში -->
<link rel="stylesheet"
      href="//cdn.web-fonts.ge/fonts/bpg-nateli/css/bpg-nateli.min.css">
/* CSS-ში */
h1, h2, h3 {
  font-family: "BPG Nateli", sans-serif;
}

დამატებით, web-fonts.ge გვთავაზობს ხელით (self-hosted) დაყენებასაც — ჩამოტვირთავ .woff/.woff2 ფაილებს და თავად წერ @font-face-ს (იხ. ქვემოთ). ხშირად ეს არჩევანია პროდაქშენ პროექტებში, სადაც გვინდა სრული კონტროლი ჩატვირთვაზე და დამოკიდებულება არ გვქონდეს გარე CDN-ზე.

@font-face — საკუთარი (self-hosted) ფონტის ხელით დამატება

როცა ფონტის ფაილები (.woff2/.woff) უკვე გაქვს ჩამოტვირთული — Google Fonts-იდანაც და web-fonts.ge-დანაც — @font-face წესით თავად აცხადებ, როგორ ერქმევა ეს ფონტი და საიდან უნდა ჩაიტვირთოს: 

@font-face {
  font-family: "BPG Nateli";
  src: url("/fonts/bpg-nateli.woff2") format("woff2"),  /* თანამედროვე, პატარა ზომის ფორმატი — პირველ რიგში */
       url("/fonts/bpg-nateli.woff") format("woff");    /* fallback ძველი ბრაუზერებისთვის */
  font-weight: 400;
  font-display: swap;
}

body {
  font-family: "BPG Nateli", sans-serif; /* შემდეგ ჩვეულებრივად გამოიყენება */
}

src-ში ჩამონათვალი — ბრაუზერი ცდის მარცხნიდან მარჯვნივ და იყენებს პირველივე ფორმატს, რომელსაც უჭერს მხარს. font-display: swap აქაც იგივეს აკეთებს, რასაც Google Fonts-ის URL-პარამეტრი — ტექსტს მალევე აჩენს fallback ფონტით.

Google Fonts CDN vs საკუთარი ჰოსტინგი

Google-ის ოფიციალური მონაცემებით, Google Fonts-ის CDN-იდან ფონტის ჩატვირთვისას მომხმარებლის ბრაუზერი პირდაპირ აგზავნის მოთხოვნას Google-ის სერვერზე — რაც გულისხმობს მომხმარებლის IP მისამართის გადაცემას.

პრაქტიკული დასკვნა: სასწავლო/პირად პროექტში Google Fonts-ის ჩვეულებრივი <link>-ით დაკავშირება სავსებით მისაღებია (ეს კურსიც ასეა აწყობილი). პროფესიული აუდიტორიისთვის განკუთვნილ პროექტში კი, ხშირად ჯობია ფონტების თვითდაჰოსტვა (@font-face-ის გამოყენებით, საკუთარ სერვერზე ატვირთული ფაილებით) — რაც სრულად გამორიცხავს მესამე მხარის სერვერთან კავშირს .

საუკეთესო პრაქტიკა — ქართული და ლათინური ერთ font stack-ში

რეალურ პროექტში ტექსტი ხშირად შერეულია — ქართული სიტყვები, ლათინური ტერმინები, ციფრები. font-family-ში რამდენიმე ფონტის ჩამონათვალი (fallback ჯაჭვი) უზრუნველყოფს, რომ ყოველი სიმბოლო „დაიჭიროს" შესაბამისმა ფონტმა: 

body {
  font-family: "Noto Sans Georgian", "Noto Sans", Arial, sans-serif;
  /* 1. Noto Sans Georgian — ქართული ასოებისთვის
     2. Noto Sans — იმავე ოჯახის ლათინური ვერსია, თანმიმდევრული სტილისთვის
     3. Arial — სისტემური fallback, თუ Google Fonts ვერ ჩაიტვირთა
     4. sans-serif — საბოლოო, გენერიკული fallback, ყოველთვის არსებობს ყველა მოწყობილობაზე */
}

5. Figma — დიზაინიდან კოდამდე

აქამდე ყველა მაგალითში ფერების, ზომებისა და ფონტების მნიშვნელობებს ჩვენ თვითონ ვწერდით. რეალურ სამუშაოში კი front-end დეველოპერი, ჩვეულებრივ, იღებს მზა დიზაინს Figma-ში და მისი ამოცანაა, ზუსტად ეს დიზაინი გადააქციოს HTML/CSS-ად.

Figma არის ბრაუზერზე დაფუძნებული (და დესკტოპ) UI/UX დიზაინის ინსტრუმენტი — დღეს ინდუსტრიის სტანდარტი ინტერფეისების დიზაინისთვის, ისევე როგორც VS Code სტანდარტია კოდისთვის. მისი მთავარი უპირატესობა — რეალურ დროში თანამშრომლობა (რამდენიმე ადამიანი ერთდროულად მუშაობს ერთსა და იმავე ფაილზე, Google Docs-ის მსგავსად).

ძირითადი ცნებები, რომლებიც დეველოპერს სჭირდება

  • Frame — დიზაინის „ტილო", რომელიც წარმოადგენს ერთ ეკრანს/გვერდს კონკრეტული სიგანით (მაგ. 1440px დესკტოპისთვის, 375px მობილურისთვის) — პირდაპირ პარალელურია HTML-ის <body>-სთან.
  • Layers პანელი — მარცხენა მხარეს, იერარქიული სია ყველა ელემენტისა — ზუსტად ისე, როგორც DevTools-ის Elements ტაბი DOM-ს აჩვენებს.
  • Auto Layout — Figma-ის ფუნქცია, რომელიც თითქმის პირდაპირ შეესაბამება CSS Flexbox-ს (შემდეგ გაკვეთილში ვისწავლით): აქვს მიმართულება (row/column), gap, padding — დიზაინერი, რომელიც Auto Layout-ს იყენებს, ფაქტობრივად უკვე „ფიქრობს" Flexbox-ის ტერმინებში.
  • კომპონენტები და ვარიანტები — ხელახლა გამოსაყენებელი ელემენტები (ღილაკი, card) სხვადასხვა მდგომარეობით (hover, disabled) — კონცეპტუალურად იგივეა, რასაც React-ის კომპონენტებში მოგვიანებით ვნახავთ.

Inspect / Dev Mode — ზუსტი CSS მნიშვნელობების ამოღება

როცა Figma-ში ირჩევ ელემენტს, მარჯვენა პანელში ჩანს ზუსტი მნიშვნელობები — ფერის hex კოდი, ზომები, ფონტის დეტალები — თითქმის მზა CSS-ის სახით: 

/* Figma-ს Inspect პანელიდან წაკითხული მონაცემები, პირდაპირ CSS-ად გადატანილი */
.btn-primary {
  background-color: #146B5C;   /* Fill — Figma-ში ჩანს ზუსტად ეს hex კოდი */
  border-radius: 8px;          /* Corner radius */
  padding: 12px 24px;           /* Auto Layout-ის padding */
  font-family: "Inter";        /* Text-ის თვისებებიდან */
  font-size: 16px;
  font-weight: 600;
  line-height: 1.5;             /* ხშირად "Line height" პროცენტულადაა Figma-ში (150%) — 1.5-ად გადაიყვანება */
}

ბევრ Figma ფაილში შესაძლებელია პირდაპირ „Copy as CSS" ღილაკის დაჭერაც — ეს ავტომატურად აკოპირებს არჩეული ელემენტის სტილს, თითქმის მზა CSS ბლოკის სახით (თუმცა ხშირად საჭიროებს მცირე „გასუფთავებას" და საკუთარ დიზაინ-სისტემასთან შესაბამისობაში მოყვანას — მაგ. ჩვენს style.css-ში უკვე განსაზღვრული var(--accent)-ის გამოყენებას, ახალი, ცალკე hex კოდის ნაცვლად).

Assets-ის ექსპორტი

სურათებისა და ხატულების (icons) მისაღებად, Figma-ში შესაძლებელია მათი ექსპორტი სხვადასხვა ფორმატში (PNG, SVG, WebP) და გარჩევადობაში — ეს პირდაპირ უკავშირდება მე-3 გაკვეთილში ნასწავლ srcset-ის (1x/2x/3x ვერსიები სხვადასხვა ეკრანის სიმკვრივისთვის) და <picture>-ის (WebP/AVIF ფორმატების) ცოდნას.

გაიმეორე — შეკითხვები

  1. რატომ არ არის საკმარისი font-family: "Noto Sans Georgian";-ის ჩაწერა, თუ ეს ფონტი წინასწარ არსად „მოტანილია"?
  2. რა განსხვავებაა Google Fonts-სა და web-fonts.ge-ს შორის — რომელ შემთხვევაში აირჩევდი თითოეულს?
  3. რას აკეთებს font-display: swap და რატომ არის ის მნიშვნელოვანი მომხმარებლის გამოცდილებისთვის?
  4. რატომ წერენ src-ში ჩვეულებრივ ჯერ .woff2-ს და მხოლოდ შემდეგ .woff-ს?
  5. რატომ შეიძლება იყოს პრობლემური Google Fonts-ის პირდაპირ CDN-იდან ჩატვირთვა ევროპული აუდიტორიისთვის, და რა არის გამოსავალი?
  6. რატომ სჭირდება front-end დეველოპერს Figma-ს ცოდნა, თუნდაც ის თავად დიზაინს არ ქმნიდეს?
  7. რა არის Figma-ს Frame და რას შეესაბამება ის HTML-ში?
  8. რატომ არის Auto Layout მნიშვნელოვანი ცნება front-end დეველოპერისთვის კონკრეტულად?
  9. რას გაძლევს Figma-ს Inspect/Dev Mode პანელი და როგორ გამოვიყენებთ ამ ინფორმაციას CSS-ში?
  10. რატომ არ არის საკმარისი Figma-დან „Copy as CSS"-ის კოდის პირდაპირ ჩასმა, ცვლილების გარეშე?

პრაქტიკული დავალებები

  1. შექმენი 3 ელემენტი — ერთი block, ერთი inline, ერთი inline-block — და დააკვირდი, როგორ განსხვავდება მათი განლაგება.
  2. დამალე ერთი ელემენტი display: none-ით და შეამოწმე DevTools-ში, რომ ის საერთოდ აღარ იკავებს სივრცეს.
  3. დაუყენე ერთ სექციას ფონის ფერი და მეორეს — ფონის სურათი cover და center პარამეტრებით.
  4. დაასტილე ერთი აბზაცი: შეცვალე font-size, line-height, letter-spacing და text-align.
  5. გახსენი fonts.google.com, აირჩიე ერთი ლათინური ფონტი, აიღე მისი embed კოდი და გამოიყენე შენს პროექტში სათაურებისთვის.
  6. გახსენი web-fonts.ge, აირჩიე ერთი ტრადიციული ქართული ფონტი (მაგ. BPG ოჯახიდან), დაუკავშირე CDN-ით და შეადარე ვიზუალურად Google Fonts-ის Noto Sans Georgian-თან.
  7. დაწერე @font-face წესი, თითქოს საკუთარ სერვერზე ატვირთული ფონტის ფაილები გაქვს (.woff2/.woff ორივე), font-display: swap-ის გამოყენებით.
  8. ააწყვე font stack მინიმუმ 3 ფონტით (ქართული ფონტი → ლათინური ანალოგი → სისტემური fallback) და გამოსცადე, რა ხდება, თუ პირველი ფონტის სახელს შეგნებულად შეცდომით (typo-თი) ჩაწერ.
  9. შექმენი უფასო Figma ანგარიში (figma.com), გახსენი ნებისმიერი საჯარო, გასაზიარებელი (community) design ფაილი, აირჩიე ერთი ღილაკი და Inspect პანელში ნახე მისი ზუსტი ფერი, padding და ფონტის მნიშვნელობები.
  10. იგივე Figma ღილაკის მონაცემები (ფერი, padding, border-radius, ფონტი) გადაიტანე რეალურ CSS-ში — ააწყვე HTML ღილაკი, რომელიც ვიზუალურად რაც შეიძლება ახლოს იმეორებს დიზაინს.
  11. (რთული) ააწყვე მარტივი „ბარათი" (card): ჩარჩო, ფონის ფერი, სათაური განსხვავებული ფონტის სისქით და ტექსტი — გამოიყენე ერთდროულად box model, display და ტექსტის თვისებები. თუ გინდა, ჯერ დახატე (ან იპოვე) ამ ბარათის დიზაინი Figma-ში და მხოლოდ შემდეგ დაწერე კოდი — ეს ზუსტად ის workflow-ია, რასაც რეალურ სამუშაოში გამოიყენებ.
