1. Props — მონაცემები „მშობლიდან შვილზე"

Props (properties) არის ის გზა, რომლითაც მშობელი კომპონენტი მონაცემებს გადასცემს შვილ კომპონენტს — ისევე, როგორც HTML ატრიბუტს ვწერთ: 

// Card.jsx — იღებს props-ს, როგორც პარამეტრს (ჩვეულებრივ, destructuring-ით)
function Card({ title, price }) {
  return (
    <div className="card">
      <h3>{title}</h3>
      <p>{price}₾</p>
    </div>
  );
}

// App.jsx — props-ის გადაცემა, ატრიბუტების მსგავსად
<Card title="React წიგნი" price={35} />

props არის read-only — შვილ კომპონენტს არ შეუძლია საკუთარი props-ის უშუალო შეცვლა. ეს არის React-ის ერთ-ერთი ფუნდამენტური წესი (ცალმხრივი მონაცემთა ნაკადი — one-way data flow). მონაცემი მიედინება ზემოდან ქვემოთ; თუ შვილს მშობლისთვის რაიმეს „თქმა" უნდა, მშობელი მას ფუნქციას გადასცემს (იხ. ქვემოთ).

რა შეიძლება გადაეცეს prop-ად

სტრიქონი ბრჭყალებით, ყველაფერი დანარჩენი — ფიგურული ფრჩხილებით:

<Product
  name="ყურსასმენი"            // სტრიქონი
  price={89.9}                  // რიცხვი
  inStock={true}                // boolean (მოკლედ: უბრალოდ  inStock )
  tags={["აუდიო", "უსადენო"]}   // მასივი
  seller={{ id: 7, name: "ლანა" }}  // ობიექტი (გარე {} — JSX, შიდა {} — ობიექტი)
  onBuy={() => alert("ნაყიდია!")}  // ფუნქცია
/>

ნაგულისხმევი მნიშვნელობა და children

function Button({ children, variant = "primary", ...rest }) {
  return (
    <button className={"btn btn-" + variant} {...rest}>
      {children}
    </button>
  );
}

// გამოყენება:
<Button>შენახვა</Button>
<Button variant="danger" onClick={handleDelete}>წაშლა</Button>
  • children — ის, რაც ტეგებს შორის ჩავწერეთ; კომპონენტებს საშუალებას აძლევს „შეფუთონ" სხვა შიგთავსი (ბარათი, მოდალი, განლაგება).
  • ...rest და {"{...rest}"} — დანარჩენი props-ის „გადაგზავნა" ჩაშენებულ ელემენტზე (onClick, disabled, aria-* და ა.შ.).
  • ნაგულისხმევი მნიშვნელობა — destructuring-ში (variant = "primary"). ეს თანამედროვე წესია; defaultProps ფუნქციურ კომპონენტებში React 19-ში ამოღებულია.
  • React 19-ში ref ჩვეულებრივი prop-ია ფუნქციურ კომპონენტში (forwardRef აღარ არის საჭირო).

Props-ის ტიპების შემოწმება

ძველი PropTypes შემოწმება React 19-ში აღარ მუშაობს (ბიბლიოთეკის პაკეტი ჯერ არსებობს, მაგრამ React მას აღარ ამოწმებს). ტიპებისთვის დღეს ჩვეულებრივ TypeScript გამოიყენება (--template react-ts); ჩვენს JavaScript პროექტებში მნიშვნელოვანია კარგი სახელები და კონსოლის გაფრთხილებებზე ყურადღება.

ფუნქციის გადაცემა: შვილიდან მშობლისკენ „კომუნიკაცია"

მონაცემი ქვემოთ მიედინება, ივენთი — ზემოთ. მშობელი გადასცემს ფუნქციას, შვილი კი მას საჭირო მომენტში იძახებს: 

function Parent() {
  const [message, setMessage] = useState("");

  return (
    <>
      <p>შეტყობინება: {message}</p>
      <Child onSend={(text) => setMessage(text)} />
    </>
  );
}

function Child({ onSend }) {
  return <button onClick={() => onSend("გამარჯობა მშობელო!")}>გაგზავნა</button>;
}

ამ პრინციპს ჰქვია state-ის ამაღლება (lifting state up): როცა ორ ან მეტ კომპონენტს ერთი და იგივე მონაცემი სჭირდება, state-ს მათ უახლოეს საერთო მშობელში ვინახავთ და props-ებით ვუზიარებთ.

Prop drilling

თუ props-ს ბევრ დონეზე გადასცემ იმ კომპონენტებს, რომლებსაც თვითონ არ სჭირდებათ, ამას ჰქვია prop drilling. მცირე აპლიკაციებში ეს ნორმალურია. როცა გაუსაძლისი გახდება, გამოიყენება useContext (ან state მენეჯმენტის ბიბლიოთეკა) — ეს ბოლო გაკვეთილზე გვექნება; ახლა ორი-სამი დონე საკმარისია.

2. State — useState Hook

State არის მონაცემი, რომელსაც კომპონენტი თავად ფლობს და თავად ცვლის დროთა განმავლობაში (მაგ. მომხმარებლის მოქმედების პასუხად). useState არის React-ის Hook, რომელიც კომპონენტს state-ის დამატების საშუალებას აძლევს: 

import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0); // [მიმდინარე მნიშვნელობა, განახლების ფუნქცია]

  return (
    <div>
      <p>დაწკაპუნებულია: {count} ჯერ</p>
      <button onClick={() => setCount(count + 1)}>
        დაწკაპუნება
      </button>
    </div>
  );
}

მნიშვნელოვანი წესი: state არასდროს არ იცვლება პირდაპირ (count = count + 1 ❌) — ყოველთვის setCount-ის მსგავსი „setter" ფუნქციით. სწორედ ეს გამოძახება ეუბნება React-ს, ხელახლა გამოსახოს (re-render) კომპონენტი ახალი მონაცემით. რჩევა: ჩვეულებრივ ცვლადს (let count) კომპონენტი რენდერებს შორის ვერ დაიმახსოვრებს — ფუნქცია ყოველ რენდერზე თავიდან სრულდება. state კი React-ის „მეხსიერებაშია".

State არის „სნეპშოტი" ყოველი რენდერისთვის

ერთ რენდერში count-ის მნიშვნელობა უცვლელია — setter-ის გამოძახება ახალ რენდერს აგეგმავს და ახალ ცვლადს ქმნის. ამიტომ შემდეგი კოდი მხოლოდ +1-ს იძლევა და არა +3-ს: 

function handleClick() {
  setCount(count + 1); // count = 0 → დაგეგმილია 1
  setCount(count + 1); // count ისევ 0-ია → დაგეგმილია 1
  setCount(count + 1); // count ისევ 0-ია → დაგეგმილია 1
}                      // შედეგი: 1

// გამოსწორება — updater (განახლების) ფუნქცია: იღებს ყველაზე ახალ მნიშვნელობას
function handleClick() {
  setCount((c) => c + 1);
  setCount((c) => c + 1);
  setCount((c) => c + 1);
}                      // შედეგი: 3

წესი: როცა ახალი state წინაზეა დამოკიდებული (+1, სიაში დამატება, toggle), გამოიყენე updater ფორმა: setX(prev => ...). React ერთ event handler-ში მრავალ განახლებას ერთ რენდერად აჯგუფებს (batching) და თუ ახალი მნიშვნელობა იგივეა (Object.is-ით), არც ახლიდან ხატავს.

ობიექტები და მასივები — არასდროს „მუტაცია"

React ადარებს მიმართვას (reference), არა შიგთავსს. ამიტომ ობიექტი ან მასივი state-ში არ უნდა შეიცვალოს (push, splice, obj.x = 1) — ყოველთვის ახალი ასლი შექმენი:

მოქმედება❌ არ გააკეთო (მუტაცია)✅ გააკეთე (ახალი ასლი)
მასივში დამატებაarr.push(x)setArr(prev => [...prev, x])
წაშლაarr.splice(i, 1)setArr(prev => prev.filter(i => i.id !== id))
ელემენტის შეცვლაarr[i].done = truesetArr(prev => prev.map(i => i.id === id ? { ...i, done: true } : i))
ობიექტის ველის შეცვლაuser.name = "..."setUser(prev => ({ ...prev, name: "..." }))
დახარისხებაarr.sort()setArr(prev => [...prev].sort(...)) ან toSorted()

კონტროლირებადი input (controlled component)

ფორმის ველი „კონტროლირებადია", როცა მისი მნიშვნელობა state-ში ინახება და ყოველი ცვლილება state-ს ანახლებს — React ხდება „ჭეშმარიტების ერთადერთი წყარო": 

function NameForm() {
  const [name, setName] = useState("");

  function handleSubmit(e) {
    e.preventDefault();               // გვერდის გადატვირთვის შეჩერება
    alert("გამარჯობა, " + name);
    setName("");                      // ველის გასუფთავება
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={name} onChange={(e) => setName(e.target.value)} />
      <button type="submit" disabled={name.trim() === ""}>გაგზავნა</button>
    </form>
  );
}

ზოგადი რჩევები state-ზე

  • ნუ შეინახავ იმას, რაც გამოითვლება. თუ შეგიძლია tasks-იდან გამოთვალო doneCount, ცალკე state არ გჭირდება — უბრალოდ გამოთვალე რენდერისას (const doneCount = tasks.filter(t => t.done).length). ორი state-ის სინქრონიზაცია ბაგების ნაყოფიერი წყაროა.
  • State-ს იკავებს მინიმუმი. იფიქრე: რა არის ის უმცირესი მონაცემი, რომლიდანაც მთელი UI აიგება.
  • თითოეულ კომპონენტის ეგზემპლარს საკუთარი state აქვს. ორი <Counter /> ერთმანეთისგან დამოუკიდებელია.
  • ლენივი (lazy) საწყისი მნიშვნელობა: თუ საწყისი მნიშვნელობის გამოთვლა „ძვირია", გადაეცი ფუნქცია: useState(() => readFromStorage()) — ის მხოლოდ პირველ რენდერზე გაეშვება.
  • state-ის გადატვირთვა key-ით: <Profile key={userId} /> — როცა key იცვლება, React კომპონენტს თავიდან ქმნის და მისი state ნულდება.

3. List & Keys

მასივის რენდერისთვის ვიყენებთ map()-ს (მე-12 გაკვეთილიდან უკვე ნაცნობი) — JSX-ში პირდაპირ ჩასმით: 

const products = [
  { id: 1, name: "წიგნი" },
  { id: 2, name: "ყურსასმენი" },
];

function ProductList() {
  return (
    <ul>
      {products.map(product => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  );
}

key ატრიბუტი აუცილებელია — ეს არის უნიკალური იდენტიფიკატორი, რომლითაც React ცნობს, რომელი ელემენტი შეიცვალა, დაემატა თუ წაიშალა სიაში. საუკეთესოა გამოვიყენოთ მონაცემის უნიკალური ID (არა მასივის index, თუ სია დინამიურად იცვლება).

key-ის წესები

  • უნიკალური „და-ძმებს" შორის (სიის ფარგლებში; გლობალურად უნიკალური არ არის საჭირო).
  • სტაბილური — ერთი და იგივე მონაცემი ყოველთვის ერთი და იგივე key-ით. key={Math.random()} ცუდია: ყოველ რენდერზე ყველა ელემენტი თავიდან იქმნება და state იკარგება.
  • key იწერება .map()-დან დაბრუნებულ გარე ელემენტზე, არა მის შიგნით.
  • key კომპონენტს props-ად არ ეგზავნება; თუ შვილს ID სჭირდება, ცალკე გადაეცი (id={"{item.id}"}).
  • ID-ის გენერირება სჯობს მონაცემის შექმნისას (crypto.randomUUID(), ან ბაზის ID), არა რენდერისას.
  • როცა ერთ იტერაციაზე რამდენიმე ელემენტია, გამოიყენე <Fragment key={"{id}"}>...</Fragment> (მოკლე <> key-ს ვერ იღებს).

რატომ არ გამოდგება index (ინდექსი) key-ად?

თუ სიას დაამატებ დასაწყისში, წაშლი შუიდან ან დაალაგებ, ინდექსები „გადაინაცვლებს" მონაცემებისგან დამოუკიდებლად — React შეცდომით მიიჩნევს, რომ პირველი <li> იგივეა, რაც იყო, და მას თავისი state (მაგ. ჩაწერილი ტექსტი input-ში, ჩეკბოქსი) „შერჩება". შედეგი: ბაგები, რომლებიც ძნელი საპოვნელია. index მისაღებია მხოლოდ სტატიკური სიისთვის, რომელიც არასდროს იცვლება.

სიების გაფილტვრა, დახარისხება, ცარიელი მდგომარეობა

function TaskList({ tasks, filter }) {
  // გამოთვლა რენდერისას — არ არის საჭირო ცალკე state
  const visible = tasks.filter((t) =>
    filter === "all" ? true : filter === "done" ? t.done : !t.done
  );

  if (visible.length === 0) {
    return <p>დავალებები არ არის.</p>;   // ცარიელი მდგომარეობა
  }

  return (
    <ul>
      {visible.map((t) => <li key={t.id}>{t.text}</li>)}
    </ul>
  );
}

4. useEffect Hook

useEffect გამოსადეგია „გვერდითი ეფექტებისთვის" (side effects) — მოქმედებები, რომლებიც კომპონენტის რენდერის მიღმა ხდება: API მოთხოვნები, ტაიმერები, event listener-ები. უფრო ზუსტად, useEffect კომპონენტს გარე სისტემასთან ასინქრონიზებს (ბრაუზერის API, ქსელი, ტაიმერი, ბიბლიოთეკა), როცა ეს სინქრონიზაცია გამოწვეულია იმით, რომ კომპონენტი ეკრანზეა. 

import { useState, useEffect } from "react";

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    // ეს კოდი სრულდება კომპონენტის რენდერის შემდეგ
    fetch(`/api/users/${userId}`)
      .then(res => res.json())
      .then(data => setUser(data));
  }, [userId]); // dependency მასივი — ეფექტი ხელახლა სრულდება, თუ userId შეიცვალა

  if (!user) return <p>იტვირთება...</p>;
  return <h2>{user.name}</h2>;
}

Lifecycle კონცეფცია Hooks-ის კონტექსტში: ძველ, class-კომპონენტებში არსებობდა ცალკეული მეთოდები (componentDidMount, componentDidUpdate) „ცხოვრების ციკლის" სხვადასხვა მომენტისთვის. useEffect ერთ Hook-ში აერთიანებს ამ ყველა შემთხვევას — dependency მასივის მეშვეობით:

  • useEffect(fn, []) — სრულდება მხოლოდ ერთხელ, კომპონენტის პირველი გამოსახვისას (mount).
  • useEffect(fn, [dep]) — სრულდება პირველად, და შემდეგ ყოველთვის, როცა dep იცვლება.
  • useEffect(fn) (მასივის გარეშე) — სრულდება ყოველი რენდერის შემდეგ (იშვიათად გამოსადეგია).

Cleanup (გასუფთავების) ფუნქცია

ეფექტმა შეიძლება დააბრუნოს ფუნქცია — ის გაეშვება ეფექტის შემდეგ გაშვებამდე და კომპონენტის მოხსნისას (unmount). იქ ვაუქმებთ ყველაფერს, რაც ეფექტმა დააყენა: 

function Clock() {
  const [now, setNow] = useState(() => new Date());

  useEffect(() => {
    const id = setInterval(() => setNow(new Date()), 1000); // setup
    return () => clearInterval(id);                          // cleanup
  }, []);

  return <p>{now.toLocaleTimeString("ka-GE")}</p>;
}

function WindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);               // setup
    return () => window.removeEventListener("resize", onResize); // cleanup
  }, []);

  return <p>ფანჯრის სიგანე: {width}px</p>;
}

წესი: ყოველ „დაყენებას" (setInterval, addEventListener, ბმა, გამოწერა) უნდა ჰქონდეს „მოხსნა" cleanup-ში.

რატომ ეშვება ეფექტი ორჯერ development-ში?

თუ პროექტში <StrictMode> ჩართულია (Vite-ის შაბლონში ჩართულია), development-ში React კომპონენტს „დაამონტაჟებს → გაასუფთავებს → ხელახლა დაამონტაჟებს". ეს განზრახ ხდება, რომ აღმოჩნდეს ეფექტები, რომლებსაც cleanup აკლიათ. production-ში ეფექტი ერთხელ სრულდება. ნუ ებრძვი ამას რეფით ან „flag-ით" — სწორი გამოსავალი არის კარგი cleanup, რომ „setup → cleanup → setup" ისე იმუშაოს, როგორც ერთი setup.

მონაცემების წამოღება: race condition და cleanup

როცა userId სწრაფად იცვლება, ორი მოთხოვნა „ეჯიბრება" ერთმანეთს და ნელი, ძველი პასუხი შეიძლება ახალს გადააწეროს. გამოსავალი — ძველი პასუხის იგნორირება cleanup-ში (ოფიციალური მიდგომა) ან მოთხოვნის გაუქმება AbortController-ით: 

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [error, setError] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    const controller = new AbortController();
    setLoading(true);
    setError(null);

    fetch(`https://jsonplaceholder.typicode.com/users/${userId}`, { signal: controller.signal })
      .then((res) => {
        if (!res.ok) throw new Error("HTTP " + res.status);
        return res.json();
      })
      .then((data) => setUser(data))
      .catch((err) => {
        if (err.name !== "AbortError") setError(err.message); // გაუქმება შეცდომად არ ითვლება
      })
      .finally(() => {
        if (!controller.signal.aborted) setLoading(false);
      });

    return () => controller.abort(); // cleanup: ძველი მოთხოვნის გაუქმება
  }, [userId]);

  if (loading) return <p>იტვირთება...</p>;
  if (error) return <p>შეცდომა: {error}</p>;
  return <h2>{user.name}</h2>;
}

ალტერნატიული, უფრო მარტივი ვარიანტი: let ignore = false; ეფექტში, ignore = true cleanup-ში და if (!ignore) setUser(...) პასუხის მიღებისას. რეალურ პროექტებში მონაცემების წამოღებას ხშირად ბიბლიოთეკები (TanStack Query, SWR) ან ფრეიმვორქები ერთვებიან — ისინი იზოლირებულად ხსნიან ქეშირების, განმეორების და race condition-ის პრობლემებს; ახლა კი ვსწავლობთ საფუძველს.

async ფუნქცია პირდაპირ ეფექტად არ გადაეცემა

useEffect(async () => {...}) არასწორია: async ფუნქცია Promise-ს აბრუნებს, React კი მოელის ან არაფერს, ან cleanup ფუნქციას. დააწერე async ფუნქცია ეფექტის შიგნით და გამოიძახე იქვე: useEffect(() => { async function load() {...} load(); }, []).

dependency მასივი: წესები

  • ჩამოთვალე ყველა რეაქტიული მნიშვნელობა, რომელსაც ეფექტი კითხულობს (props, state, მათგან გამოთვლილი ცვლადები). React-ის ESLint პლაგინი (eslint-plugin-react-hooks, შაბლონში უკვე ჩართულია) ამას გაჩვენებს.
  • ნუ „დაჩუმებ" ლინტერს, თუ მასივს არასწორად ამოკლებ — ეფექტი „ძველ" მნიშვნელობებს დაინახავს (stale closure).
  • ობიექტი ან ფუნქცია, რომელიც რენდერში იქმნება, ყოველ ჯერზე ახალი მიმართვაა → ეფექტი ყოველ რენდერზე გაეშვება. გადაიტანე ეფექტის შიგნით ან დაამუშავე პრიმიტიულ მნიშვნელობამდე (user.id და არა user).
  • უსასრულო ციკლი: ეფექტი ანახლებს state-ს, რომელიც თავად არის dependency → ახალი რენდერი → ისევ ეფექტი... შეამოწმე, უნდა ანახლებდეს თუ არა ეფექტი ამ state-ს საერთოდ.

useEffectEvent (React 19.2+)

ხანდახან ეფექტს ესაჭიროება მიმდინარე მნიშვნელობის „წაკითხვა", მაგრამ ამ მნიშვნელობის ცვლილებამ ეფექტი თავიდან არ უნდა გაუშვას (მაგ. ჩატის ოთახთან კავშირი უნდა გაიხსნას მხოლოდ roomId-ის ცვლილებისას, მაგრამ შეტყობინებაში მიმდინარე theme-ი უნდა გამოვიყენოთ). ამისთვის React 19.2-ში stable გახდა useEffectEvent: 

import { useEffect, useEffectEvent } from "react";

function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showNotification("დაკავშირებულია!", theme); // ყოველთვის მიმდინარე theme-ს ხედავს
  });

  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on("connected", () => onConnected());
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]); // theme dependency არ არის
}

ეს გაკვეთილისთვის „ბონუს-ცნებაა" — მთავარია გესმოდეს, რომ ასეთი ხელსაწყო არსებობს. ესენი createConnection და showNotification პირობითი ფუნქციებია მაგალითისთვის.

გახსოვდეს: „You Might Not Need an Effect"

ეფექტი ხშირად ზედმეტია. React-ის დოკუმენტაცია აკონკრეტებს, რომ ეფექტი არ გჭირდება, როცა:

  • მონაცემს გამოთვლი props-ებიდან ან state-იდან — გამოთვალე პირდაპირ რენდერისას (არა useEffect + setState).
  • მომხმარებლის ქმედებას ამუშავებ (დაჭერა, გაგზავნა) — ეს event handler-ში ხდება, არა ეფექტში.
  • state-ის გადატვირთვა გინდა prop-ის შეცვლისას — გამოიყენე key.

კარგი წესი: თუ რაღაც გამოწვეულია ქმედებით — event handler; თუ იმით, რომ კომპონენტი ეკრანზეა და გარე სისტემასთან უნდა იყოს სინქრონში — useEffect.

Class lifecycle ↔ useEffect — ცხრილი

Class (ძველი)Hooks (დღევანდელი)

componentDidUpdateuseEffect(() => {...}, [dep])
componentWillUnmountეფექტის cleanup: return () => {...}

ეს შესაბამისობა მიახლოებითია: Hooks-ში ფიქრობენ არა „როდის", არამედ „რასთან სინქრონიზაცია": ეფექტი აღწერს, როგორ დაიწყოს და როგორ შეწყვიტოს სინქრონიზაცია, ხოლო React გადაწყვეტს, როდის გაუშვას. ასევე არსებობს useLayoutEffect — ის ეკრანის დახატვამდე სრულდება და DOM-ის გაზომვისთვის გამოიყენება; იშვიათია.

5. useRef Hook

useRef ქმნის „კონტეინერს", რომლის მნიშვნელობის შეცვლა არ იწვევს ხელახალ რენდერს (განსხვავებით useState-ისგან). ორი ძირითადი გამოყენებაა: 

import { useRef, useEffect } from "react";

function SearchInput() {
  const inputRef = useRef(null); // 1. პირდაპირი წვდომა DOM ელემენტზე

  useEffect(() => {
    inputRef.current.focus(); // კომპონენტის ჩატვირთვისას, input ავტომატურად ფოკუსირდება
  }, []);

  return <input ref={inputRef} type="text" />;
}
// 2. მნიშვნელობის შენახვა რენდერებს შორის, ხელახალი რენდერის გამოწვევის გარეშე
function Timer() {
  const renderCount = useRef(0);
  renderCount.current++; // იზრდება, მაგრამ არ იწვევს ხელახალ რენდერს
  return <p>ეს კომპონენტი გამოისახა {renderCount.current} ჯერ</p>;
}

ყურადღება: ზემოთ Timer-ის მაგალითი მხოლოდ ილუსტრაციაა. React-ის რეკომენდაციით ref.current რენდერისას არ უნდა იკითხებოდეს ან იწერებოდეს (გარდა საწყისი ინიციალიზაციისა) — ეს რენდერს „არასუფთას" ხდის და StrictMode-ში მნიშვნელობა „ორჯერ" გაიზრდება. რეფის ცვლილებები ეფექტებში ან event handler-ებში უნდა მოხდეს.

useRef-ის ტიპური გამოყენებები

  • DOM-ზე წვდომა: focus(), scrollIntoView(), ვიდეოს play(), ზომის გაზომვა.
  • ტაიმერის ID-ის შენახვა: timerRef.current = setTimeout(...), რომ შემდეგ clearTimeout გამოვიძახოთ.
  • წინა მნიშვნელობის დამახსოვრება (ეფექტში განახლებით).
  • არაკონტროლირებადი input-ები და ფაილის ველი (input type="file").
useStateuseRef

გამოიყენე, როცამნიშვნელობა ეკრანზე ჩანსმნიშვნელობა ეკრანზე არ ჩანს (DOM, ტაიმერი)

React 19-ში ref callback-ებს შეუძლიათ cleanup ფუნქციის დაბრუნება (ისევე, როგორც ეფექტებს), ხოლო ფუნქციურ კომპონენტს ref ჩვეულებრივი prop-ის სახით გადაეცემა — forwardRef აღარ არის საჭირო.

6. Hooks-ის წესები და custom hooks

Hooks-ის ორი წესი

  1. გამოიძახე Hooks მხოლოდ უმაღლეს დონეზე — არა ციკლში, არა პირობაში (if), არა ჩადგმულ ფუნქციაში. React Hooks-ს მათი გამოძახების რიგით ცნობს; რიგი ყველა რენდერზე ერთნაირი უნდა იყოს.
  2. გამოიძახე Hooks მხოლოდ React კომპონენტებიდან ან სხვა Hooks-იდან (custom hook-ებიდან), არა ჩვეულებრივი JS ფუნქციებიდან.
function Bad({ show }) {
  if (show) {
    const [x, setX] = useState(0);   // ❌ პირობაში
  }
  // ...
}

function Good({ show }) {
  const [x, setX] = useState(0);     // ✅ ყოველთვის, ზედა დონეზე
  if (!show) return null;
  // ...
}

eslint-plugin-react-hooks (Vite-ის React შაბლონში ჩართულია) ამ წესებს ავტომატურად გაკონტროლებს — არ დააიგნორო მისი გაფრთხილებები.

Custom hook — შენი საკუთარი Hook

როცა ერთი და იგივე ლოგიკა (state + ეფექტი) რამდენიმე კომპონენტში მეორდება, მას ცალკე ფუნქციად გამოვიტანთ. სახელი აუცილებლად იწყება use-თი: 

// src/hooks/useLocalStorage.js
import { useState, useEffect } from "react";

export function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try {
      const saved = localStorage.getItem(key);
      return saved !== null ? JSON.parse(saved) : initialValue;
    } catch {
      return initialValue;       // დაზიანებული ან მიუწვდომელი მეხსიერება
    }
  });

  useEffect(() => {
    try {
      localStorage.setItem(key, JSON.stringify(value));
    } catch {
      /* მეხსიერება სავსეა ან დაბლოკილია — ჩუმად გავაგრძელებთ */
    }
  }, [key, value]);

  return [value, setValue];
}

გამოყენება — ზუსტად useState-ივით, მაგრამ მონაცემი ბრაუზერის გადატვირთვის შემდეგაც რჩება: const [theme, setTheme] = useLocalStorage("theme", "light");

სხვა Hooks — რა გველოდება

Hookრისთვის
useReducerრთული state-ის ლოგიკა ერთ ფუნქციაში (useState-ის ალტერნატივა)
useContextმონაცემის გაზიარება ხეში prop drilling-ის გარეშე (თემა, მომხმარებელი)
useMemo, useCallbackგამოთვლებისა და ფუნქციების დამახსოვრება ოპტიმიზაციისთვის. React Compiler-ით უმეტესად ავტომატურდება, ამიტომ დამწყებს აუცილებლად არ სჭირდება
useIdუნიკალური ID ფორმის ველებისა და ლეიბლების დასაკავშირებლად
useActionState, useOptimistic, useReact 19-ის ახალი Hooks/API ფორმებისთვის და ასინქრონული მონაცემებისთვის — უფრო მოწინავე თემა

7. ყველაზე ხშირი შეცდომები

შეცდომასიმპტომიგამოსწორება
state-ის პირდაპირი შეცვლა: tasks.push(x) UI არ განახლდა ახალი მასივი: setTasks(prev => [...prev, x])
setCount(count + 1) რამდენჯერმე ზედიზედ მხოლოდ +1 მატება updater: setCount(c => c + 1)
state-ის წაკითხვა setter-ის შემდეგ console.log(count) ძველ მნიშვნელობას აჩვენებს ახალ მნიშვნელობას მხოლოდ შემდეგ რენდერში ნახავ; დამოკიდებული ლოგიკა — ეფექტში ან უშუალოდ გამოთვალე
onClick={"{handle()}"} (გამოძახებით) ფუნქცია რენდერისას გაეშვა; უსასრულო ციკლი onClick={"{handle}"} ან onClick={"{() => handle(id)}"}
key-ის გარეშე ან key={"{index}"} დინამიურ სიაში გაფრთხილება ან „აცდენილი" state უნიკალური, სტაბილური id
ეფექტში cleanup არ არის ორმაგი ტაიმერი/listener, მეხსიერების გაჟონვა, ეფექტი ორჯერ ეშვება dev-ში დააბრუნე cleanup ფუნქცია
ობიექტი ან ფუნქცია dependency-ში, რომელიც რენდერში იქმნება ეფექტი ყოველ რენდერზე ეშვება; უსასრულო ციკლი გადაიტანე ეფექტის შიგნით ან გამოიყენე პრიმიტივი
Hook პირობაში ან ციკლში შეცდომა „Rendered more hooks than during the previous render" Hooks-ი ყოველთვის ზედა დონეზე
ორი state, რომლებიც ერთმანეთისგან გამოითვლება სინქრონიზაციის ბაგები შეინახე ერთი, მეორე გამოთვალე რენდერისას

8. რეალური პროექტი: To-Do აპლიკაცია

ახლა ყველაფერს ერთ პროექტში ვაერთიანებთ: ავაწყობთ დავალებების მენეჯერს. ის ერთდროულად იყენებს გაკვეთილის ყველა თემას: props, state, სიები და key-ები, useEffect, useRef და custom hook. პროექტი ისეთია, რომლის ჩვენებაც პორტფოლიოში შეიძლება.

ნაბიჯი 2. App.jsx — მთავარი state და ლოგიკა

// src/App.jsx
import { useState, useEffect } from "react";
import { useLocalStorage } from "./hooks/useLocalStorage";
import TaskForm from "./components/TaskForm";
import Filters from "./components/Filters";
import TaskList from "./components/TaskList";

function App() {
  const [tasks, setTasks] = useLocalStorage("tasks", []);
  const [filter, setFilter] = useState("all");      // "all" | "active" | "done"
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  // ── გამოთვლილი მნიშვნელობები (არა state!) ──
  const remaining = tasks.filter((t) => !t.done).length;
  const visibleTasks = tasks.filter((t) =>
    filter === "all" ? true : filter === "done" ? t.done : !t.done
  );

  // ── ეფექტი: ბრაუზერის ტაბის სათაური მიჰყვება მთვლელს ──
  useEffect(() => {
    document.title = remaining === 0 ? "To-Do" : `(${remaining}) To-Do`;
  }, [remaining]);

  // ── მოქმედებები (ყველა — updater ფორმით, ახალი ასლით) ──
  function addTask(text) {
    setTasks((prev) => [...prev, { id: crypto.randomUUID(), text, done: false }]);
  }

  function toggleTask(id) {
    setTasks((prev) => prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
  }

  function editTask(id, text) {
    setTasks((prev) => prev.map((t) => (t.id === id ? { ...t, text } : t)));
  }

  function deleteTask(id) {
    setTasks((prev) => prev.filter((t) => t.id !== id));
  }

  function clearDone() {
    setTasks((prev) => prev.filter((t) => !t.done));
  }

  // ── გარე API-დან ნიმუშის ჩატვირთვა (event handler-ში, არა ეფექტში: მომხმარებლის ქმედებაა) ──
  async function loadSamples() {
    setLoading(true);
    setError(null);
    try {
      const res = await fetch("https://jsonplaceholder.typicode.com/todos?_limit=5");
      if (!res.ok) throw new Error("სერვერის შეცდომა: " + res.status);
      const data = await res.json();
      const samples = data.map((item) => ({
        id: crypto.randomUUID(),       // ახალი ID, რომ API-ს ID-ები არ დაგვეჯახოს
        text: item.title,
        done: item.completed,
      }));
      setTasks((prev) => [...prev, ...samples]);
    } catch (err) {
      setError(err.message);
    } finally {
      setLoading(false);
    }
  }

  return (
    <main className="app">
      <h1>დავალებები</h1>

      <TaskForm onAdd={addTask} />

      <Filters current={filter} onChange={setFilter} />

      <TaskList
        tasks={visibleTasks}
        onToggle={toggleTask}
        onEdit={editTask}
        onDelete={deleteTask}
      />

      <footer className="toolbar">
        <span>დარჩენილია {remaining} დავალება</span>
        <button onClick={clearDone} disabled={tasks.every((t) => !t.done)}>
          შესრულებულების წაშლა
        </button>
        <button onClick={loadSamples} disabled={loading}>
          {loading ? "იტვირთება..." : "ნიმუშის ჩატვირთვა"}
        </button>
      </footer>

      {error && <p role="alert" className="error">{error}</p>}
    </main>
  );
}

export default App;

შეამჩნიე: remaining და visibleTasks state არ არის — ისინი გამოითვლება ყოველ რენდერზე tasks-იდან და filter-იდან. ამიტომ ისინი არასოდეს გამოვა სინქრონიდან. ასევე ყველა განახლება ახალ მასივს ქმნის (map, filter, spread) — არასდროს push.

ნაბიჯი 3. TaskForm — კონტროლირებადი input და useRef

// src/components/TaskForm.jsx
import { useState, useRef, useEffect } from "react";

function TaskForm({ onAdd }) {
  const [text, setText] = useState("");
  const inputRef = useRef(null);

  // გვერდის გახსნისას ფოკუსი input-ზე
  useEffect(() => {
    inputRef.current.focus();
  }, []);

  function handleSubmit(e) {
    e.preventDefault();
    const trimmed = text.trim();
    if (trimmed === "") return;       // ცარიელი ტექსტი არ ემატება

    onAdd(trimmed);
    setText("");
    inputRef.current.focus();         // დამატების შემდეგ ფოკუსი ისევ input-ზე
  }

  return (
    <form onSubmit={handleSubmit} className="task-form">
      <input
        ref={inputRef}
        value={text}
        onChange={(e) => setText(e.target.value)}
        placeholder="რა უნდა გააკეთო?"
        aria-label="ახალი დავალება"
      />
      <button type="submit" disabled={text.trim() === ""}>დამატება</button>
    </form>
  );
}

export default TaskForm;

<form onSubmit> იძლევა ბონუსს: Enter-ზე დაჭერა თავისით მუშაობს. e.preventDefault() აჩერებს გვერდის გადატვირთვას. StrictMode-ში focus()-ის ორჯერ გამოძახება უვნებელია — ეს კარგი „სუფთა“ ეფექტია.

TaskItem — ყველაზე საინტერესო კომპონენტი: მას საკუთარი ლოკალური state აქვს (რედაქტირების რეჟიმი) და useRef + useEffect ფოკუსისთვის: 

// src/components/TaskItem.jsx
import { useState, useRef, useEffect } from "react";

function TaskItem({ task, onToggle, onEdit, onDelete }) {
  const [isEditing, setIsEditing] = useState(false);
  const [draft, setDraft] = useState(task.text);
  const editRef = useRef(null);

  // როცა რედაქტირების რეჟიმი ირთვება — ფოკუსი და ტექსტის მონიშვნა
  useEffect(() => {
    if (isEditing) {
      editRef.current.focus();
      editRef.current.select();
    }
  }, [isEditing]);

  function startEditing() {
    setDraft(task.text);
    setIsEditing(true);
  }

  function save() {
    const trimmed = draft.trim();
    if (trimmed !== "" && trimmed !== task.text) {
      onEdit(task.id, trimmed);
    }
    setIsEditing(false);
  }

  function handleKeyDown(e) {
    if (e.key === "Enter") save();
    if (e.key === "Escape") setIsEditing(false);   // გაუქმება
  }

  return (
    <li className={task.done ? "task done" : "task"}>
      <input
        type="checkbox"
        checked={task.done}
        onChange={() => onToggle(task.id)}
        aria-label={"მონიშვნა: " + task.text}
      />

      {isEditing ? (
        <input
          ref={editRef}
          value={draft}
          onChange={(e) => setDraft(e.target.value)}
          onBlur={save}
          onKeyDown={handleKeyDown}
          aria-label="დავალების რედაქტირება"
        />
      ) : (
        <span onDoubleClick={startEditing}>{task.text}</span>
      )}

      <button onClick={() => onDelete(task.id)} aria-label={"წაშლა: " + task.text}>
        ✕
      </button>
    </li>
  );
}

export default TaskItem;

რატომ მუშაობს ეს სწორად? თითოეულ TaskItem ეგზემპლარს საკუთარი isEditing აქვს, და რადგან key={"{task.id}"} სტაბილურია, დავალების წაშლა ან გაფილტვრა სხვა ელემენტის რედაქტირების რეჟიმს არ „გადაუწევს". თუ აქ key={"{index}"} გამოგვეყენებინა, წაშლის შემდეგ რედაქტირების state-ი „არასწორ“ დავალებაზე გადავიდოდა — ზუსტად ის ბაგი, რაზეც სიების სექციაში ვილაპარაკეთ.

9. თვითშემოწმება

1. რით განსხვავდება props state-ისგან?

Props მშობლისგან მოდის და კომპონენტის შიგნით read-only არის; state კომპონენტის საკუთარი, ცვლადი მონაცემია, რომელსაც setter ფუნქციით ვცვლით და რომლის ცვლილება re-render-ს იწვევს.

2. რატომ არ შეიძლება tasks.push(x) state-ის მასივზე?

React მიმართვებს ადარებს. მასივის შიგნით ცვლილება მიმართვას არ ცვლის, ამიტომ React-ს ცვლილება არ შეატყობს და UI არ განახლდება. ახალი მასივი უნდა შევქმნათ: setTasks(prev => [...prev, x]).

3. რატომ აძლევს setCount(count+1) სამჯერ მხოლოდ +1-ს და როგორ გამოვასწოროთ?

ერთ რენდერში count სნეპშოტია, სამივე გამოძახება ერთსა და იმავე მნიშვნელობას ხედავს. გამოსწორება: setCount(c => c + 1).

4. რისთვის არის key და რატომ არ გვინდა index?

ის React-ს ეხმარება ზუსტად ამოიცნოს ელემენტები დამატებისას, წაშლისას და გადაადგილებისას. დინამიურ სიაში index „გადაინაცვლებს“ მონაცემებისგან და state შეიძლება არასწორ ელემენტს შერჩეს.

5. რას ნიშნავს ცარიელი dependency მასივი [] და რა მნიშვნელობა აქვს cleanup-ს?

[] — ეფექტი გაეშვება მხოლოდ mount-ზე (production-ში ერთხელ). cleanup ეშვება ეფექტის შემდეგ გაშვებამდე და unmount-ზე და აუქმებს ეფექტით დაყენებულს (ტაიმერი, listener, მოთხოვნა).

6. რატომ ეშვება ეფექტი ორჯერ development-ში?

StrictMode განზრახ აკეთებს mount → cleanup → mount, რომ გამოააშკარავოს ეფექტები, რომლებსაც cleanup აკლიათ. production-ში ასე არ ხდება.

7. როდის გამოვიყენოთ useRef, როდის useState?

useState — როცა მნიშვნელობა ეკრანზე ჩანს და მისმა ცვლილებამ UI უნდა განაახლოს; useRef — DOM ელემენტთან წვდომისთვის ან ისეთი მნიშვნელობის შესანახად (ტაიმერის ID), რომლის ცვლილება re-render-ს არ უნდა იწვევდეს.

8. რა არის Hooks-ის ორი ძირითადი წესი?

(1) მხოლოდ ზედა დონეზე, არა პირობაში/ციკლში/ჩადგმულ ფუნქციაში; (2) მხოლოდ React კომპონენტებიდან ან custom hook-ებიდან.

9. რატომ არის ზედმეტი useEffect, რომელიც props-იდან გამოთვლილ მნიშვნელობას state-ში წერს?

ასეთი მნიშვნელობა პირდაპირ რენდერისას უნდა გამოითვალოს. ეფექტი + ცალკე state ქმნის დამატებით რენდერს და სინქრონიზაციის ბაგების რისკს.
