CSS · 08/24 — მოდულის ბოლო გაკვეთილი

Bootstrap, Git & GitHub, რესპონსიული დიზაინი და Container Queries

CSS მოდულის ბოლო გაკვეთილი სამ პრაქტიკულ თემას აერთიანებს: მზა CSS ჩარჩოს (Bootstrap), კოდის ვერსიების მართვისა და გუნდური მუშაობის სისტემას (Git & GitHub), და იმას, თუ როგორ ვხდით საიტს ყველა ეკრანსა და კონტექსტში გამოსადეგს.

1. Bootstrap

Bootstrap არის მზა CSS (და JS) ბიბლიოთეკა, რომელიც გვთავაზობს გამზადებულ კომპონენტებს (ღილაკები, ბარათები, ნავიგაცია, მოდალები) და 12-სვეტიან grid სისტემას. მარტივი და სწრაფია, თუმცა ცოტა ამცირებს დიზაინის კონტროლს, საკუთარი CSS-თან შედარებით. ამჟამინდელი ვერსია — Bootstrap 5.3 (ბოლო patch: 5.3.8) — არ საჭიროებს jQuery-ს, აქვს ჩაშენებული Dark Mode მხარდაჭერა და CSS ცვლადებზე (custom properties) აწყობილი დიზაინ-სისტემა.

integrity ატრიბუტი (SRI — Subresource Integrity) ამოწმებს, რომ CDN-დან ჩამოტვირთული ფაილი ზუსტად ისეთია, როგორადაც გამოქვეყნდა — არავის შეუძლია მისი „ჩანაცვლება" მავნე კოდით. ეს კონკრეტული hash-ები Bootstrap-ის ოფიციალურ საიტზეა გამოქვეყნებული და ყოველი ვერსიისთვის განსხვავებულია.

Breakpoints — grid-ის ზუსტი ზღვრები

Bootstrap-ის grid სისტემა ეფუძნება 6 ზუსტ breakpoint-ს (ეკრანის სიგანის ზღვარს):

Class პრეფიქსი მინიმალური სიგანე მოწყობილობა
col-0pxყველა ეკრანი (X-Small)
col-sm-576pxტელეფონი, თარაზული
col-md-768pxტაბლეტი
col-lg-992pxლეპტოპი
col-xl-1200pxდესკტოპი
col-xxl-1400pxდიდი მონიტორი

Grid სისტემა — პრაქტიკული მაგალითი

<div class="container">         <!-- ან .container-fluid, სრული სიგანისთვის -->
  <div class="row">
    <div class="col-12 col-md-6 col-lg-4">
      <!-- მობილურზე: 12/12 (მთელი სიგანე)
           ტაბლეტზე (≥768px): 6/12 (ნახევარი)
           დესკტოპზე (≥992px): 4/12 (ერთი მესამედი) -->
      ბარათი 1
    </div>
    <div class="col-12 col-md-6 col-lg-4">ბარათი 2</div>
    <div class="col-12 col-md-6 col-lg-4">ბარათი 3</div>
  </div>
</div>

ეს Mobile-First მიდგომაა (ისევე, როგორც ხელით დაწერილ CSS-ში) — თითოეული კლასი „მინიმუმ ამ სიგანიდან" მოქმედებს, არა ზუსტად ამ სიგანეზე.

ხშირად გამოსაყენებელი კომპონენტები

<!-- ღილაკები — ფერი/ზომა/ვარიაცია utility-კლასებით -->
<button class="btn btn-primary">მთავარი</button>
<button class="btn btn-outline-secondary btn-sm">მეორადი</button>

<!-- ბარათი (Card) -->
<div class="card">
  <img src="..." class="card-img-top" alt="...">
  <div class="card-body">
    <h5 class="card-title">სათაური</h5>
    <p class="card-text">აღწერა</p>
  </div>
</div>

<!-- Alert (შეტყობინება) -->
<div class="alert alert-success" role="alert">
  წარმატებით შენახულია!
</div>

Utility კლასები — spacing, flex, ტექსტი

Bootstrap-ის ერთ-ერთი ყველაზე ხშირად გამოსაყენებელი ნაწილი — მზა „utility" კლასები, რომლებიც ერთ CSS თვისებას შეესაბამება (ჩვენი მე-6 გაკვეთილის Flexbox-ის ცოდნაც პირდაპირ გამოსადეგია აქ): 

/* Spacing: m/p + t/b/s/e/x/y + 0-5 (mt-3 = margin-top) */
<div class="mt-4 mb-2 px-3">...</div>

/* Flexbox utility-კლასები — პირდაპირ შეესაბამება მე-6 გაკვეთილს */
<div class="d-flex justify-content-between align-items-center gap-3">...</div>

/* ტექსტი და ფერები */
<p class="text-center text-muted fw-bold">...</p>

საუკეთესო პრაქტიკა: Bootstrap გამოსადეგია სწრაფი პროტოტიპირებისთვის, MVP-სთვის ან შიდა ინსტრუმენტებისთვის. თუ პროექტს სჭირდება უნიკალური, ბრენდირებული დიზაინი — ხშირად უკეთესია საკუთარი CSS სისტემის აწყობა (ისევე, როგორც ამ კურსის საიტზეა გაკეთებული), ან Bootstrap-ის Sass ცვლადების საშუალებით მორგება.

შენიშვნა:
მიმართულება: t = top(ზემოთ) b = bottom(ქვემოთ) s = start(მარცხნივ, LTR რეჟიმში) e = end(მარჯვნივ, LTR რეჟიმში) x = ჰორიზონტალურად(მარცხნივ + მარჯვნივ) y = ვერტიკალურად(ზემოთ + ქვემოთ) თუ მიმართულების ასოს არ მიუწერთ (მაგ. m-3), ოთხივე მხარეს იმოქმედებს.
ზომების შკალა (0-5):

  • 0 = 0
  • 1 = 0.25rem = 4px
  • 2 = 0.5rem = 8px
  • 3 = 1rem = 16px
  • 4 = 1.5rem = 24px
  • 5 = 3rem = 48px

2. Git — ვერსიების კონტროლის სისტემა

Git აღრიცხავს კოდის ცვლილებების ისტორიას — წინა ვერსიაზე დაბრუნებას შესაძლებელს ხდის, ასევე ამ ხელსაწყოს გამოყენებით დეველოპერებს ერთად მუშაობა შეგვიძლია ერთსა და იმავე პროექტზე. 

# პროექტის ინიციალიზაცია და პირველი commit
git init
git add .
git commit -m "პირველი commit: საწყისი სტრუქტურა"

# ცვლილებების ისტორიის ნახვა
git status
git log --oneline

git switch / git restore — თანამედროვე სტანდარტი

ძველად branch-ის გადართვისთვისაც და ფაილის აღდგენისთვისაც ერთი ბრძანება — git checkout — გამოიყენებოდა, რაც ხშირად აბნევდა (ორი, სრულიად განსხვავებული დანიშნულება ერთ ბრძანებაში). Git 2.23-დან (2019) და დღემდე, ეს ორ ცალკე, მკაფიო ბრძანებადაა გაყოფილი — 2025-2026-ის მდგომარეობით ეს არის რეკომენდებული სტანდარტი: 

# branch-ის გადართვისთვის — git switch
git switch feature/navbar        # არსებულ branch-ზე გადართვა
git switch -c feature/new-navbar # ახალი branch-ის შექმნა + გადართვა (-c = create)

# ფაილის ცვლილებების გაუქმებისთვის — git restore
git restore style.css            # ბოლო commit-ის მდგომარეობაზე დაბრუნება
git restore --staged style.css   # "staged"-იდან მოხსნა (git add-ის გაუქმება)

წესი დასამახსოვრებლად: Branch = switch. ფაილი = restore. ძველი git checkout კვლავ მუშაობს, მაგრამ ახალ პროექტებში/გუნდებში ორი ცალკე ბრძანების გამოყენება უფრო უსაფრთხო და ცალსახაა.

Commit-ების სტილი — Conventional Commits

დიდ პროექტებში/გუნდებში მიღებულია commit-ის შეტყობინებების სტანდარტიზებული ფორმატი, რომელიც commit-ის ტიპსაც გამოხატავს: 

# ცუდი: ყველაფერი ერთ commit-ში, გაურკვეველი შეტყობინება
git add .
git commit -m "fix stuff"

# კარგი: ერთი commit — ერთი ლოგიკური ცვლილება, ტიპით
git add src/auth/
git commit -m "fix(auth): expired token-ის სწორად დამუშავება"

git add README.md
git commit -m "docs: ავტორიზაციის სექციის განახლება"

ხშირად გამოსაყენებელი ტიპებია: feat (ახალი ფუნქციონალი), fix (შეცდომის გასწორება), docs (დოკუმენტაცია), style (ფორმატირება, ლოგიკის შეცვლის გარეშე), refactor (კოდის რესტრუქტურიზაცია).

git stash — დროებითი „გვერდზე გადადება"

# სამუშაო, დაუმთავრებელი ცვლილებების დროებით შენახვა
git stash push -m "მუშაობა navbar-ის დიზაინზე"

git switch main       # სხვა branch-ზე გადასვლა, სუფთა working tree-ით
# ... სასწრაფო შესწორება ...

git switch feature/navbar
git stash pop          # შენახული ცვლილებების დაბრუნება
git stash list          # ყველა stash-ის ნახვა

.gitignore — რისი აღრიცხვა არ გვინდა

ზოგიერთი ფაილი/საქაღალდე (მაგ. დამოკიდებულებები, დროებითი ფაილები) საერთოდ არ უნდა მოხვდეს Git-ის ისტორიაში: 

# .gitignore ფაილის შემცველობა
node_modules/
.DS_Store
.env
*.log
dist/

3. GitHub — თანამშრომლობა და Pull Request Workflow

GitHub არის Git-ის საფუძველზე აშენებული პლატფორმა, სადაც პროექტი ინახება ღრუბელში, ხელმისაწვდომია გუნდისთვის და შესაძლებელია პორტფოლიოს სახედაც იქცეს. 

# ლოკალური რეპოზიტორიის დაკავშირება GitHub-თან
git remote add origin https://github.com/username/front-end-course.git
git branch -M main
git push -u origin main

რეალური გუნდური workflow — Pull Request

გუნდურ პროექტში პირდაპირ main branch-ზე მუშაობა თითქმის არასდროს ხდება. სტანდარტული ციკლი ასეთია: 

# 1. ახალი, აღწერითი სახელის branch (feature/, fix/, docs/ პრეფიქსით)
git switch -c feature/dark-mode-toggle

# 2. ცვლილებები, commit-ები (Conventional Commits ფორმატით)
git add .
git commit -m "feat(theme): dark mode toggle ღილაკის დამატება"

# 3. push GitHub-ზე, ამ კონკრეტულ branch-ზე
git push -u origin feature/dark-mode-toggle

# 4. GitHub-ის საიტზე იხსნება "Pull Request" —
#    გუნდი review-ს უკეთებს, კომენტარებს სვამს, შემდეგ "Merge"-ს აწესებს main-ში

Pull Request (PR) არის ფორმალური მოთხოვნა, რომ branch-ის ცვლილებები „შეერწყას" მთავარ branch-ს — ის იძლევა შესაძლებლობას, გუნდმა კოდი გადახედოს (Code Review), ავტომატური ტესტები გაეშვას (CI), და მხოლოდ მას შემდეგ მოხდეს merge.

force push-ის საფრთხე გაზიარებულ branch-ზე: თუ ისტორია უკვე ხელახლა დაწერე (მაგ. rebase-ის შემდეგ) და ხელახლა push გჭირდება, არასდროს გამოიყენო უბრალო git push --force გაზიარებულ branch-ზე — ეს შეიძლება გადაფაროს კოლეგის ცვლილებები. სანაცვლოდ: 

# უსაფრთხო ალტერნატივა — მხოლოდ იმ შემთხვევაში "ჩაწერს", თუ ვინმეს ცვლილება არ დაგეკარგება
git push --force-with-lease

4. რესპონსიული დიზაინი და CSS Media Queries

რესპონსიული (responsive) დიზაინი ნიშნავს, რომ ერთი და იგივე HTML/CSS კარგად გამოიყურება ტელეფონზეც, ტაბლეტზეც და დიდ მონიტორზეც. ამის მთავარი, კლასიკური ინსტრუმენტია @media query — ის რეაგირებს ბრაუზერის ვიუპორტის ზომაზე. 

/* საბაზისო სტილი — მობილურისთვის (Mobile-First მიდგომა) */
.grid {
  display: grid;
  grid-template-columns: 1fr; /* ერთი სვეტი მცირე ეკრანზე */
  gap: 16px;
}

/* ტაბლეტი და მეტი (≥768px) */
@media (min-width: 768px) {
  .grid {
    grid-template-columns: repeat(2, 1fr);
  }
}

/* დესკტოპი (≥1024px) */
@media (min-width: 1024px) {
  .grid {
    grid-template-columns: repeat(3, 1fr);
  }
}

Mobile-First მიდგომა (ჯერ პატარა ეკრანისთვის ვწერთ, შემდეგ min-width-ით ვამატებთ დიდი ეკრანის სტილებს) დღეს ინდუსტრიის სტანდარტია — უფრო სუფთა და ეფექტურია, ვიდრე საწინააღმდეგო (Desktop-First, max-width-ზე დაფუძნებული) მიდგომა.

ასევე მნიშვნელოვანია <head>-ში viewport მეტა-ტეგის არსებობა (რომელსაც უკვე ვიყენებთ ამ კურსის ყველა გვერდზე): 

<meta name="viewport" content="width=device-width, initial-scale=1.0">

5. Container Queries — Media Queries-ის თანამედროვე გაგრძელება

@media-ს ერთადერთი „ბრმა წერტილი" — ის ხედავს მხოლოდ მთელი ბრაუზერის ვიუპორტის სიგანეს, არა კონკრეტული კომპონენტის სივრცეს. პრობლემა ჩნდება, როცა ერთი და იგივე კომპონენტი (მაგ. card) სხვადასხვა კონტექსტში ჩნდება — ერთხელ სრული სიგანის სექციაში, ერთხელ ვიწრო sidebar-ში — მაგრამ media query ამას ვერ არჩევს, რადგან ვიუპორტი ორივე შემთხვევაში ერთი და იგივეა.

@container query წყვეტს ზუსტად ამ პრობლემას — კომპონენტი რეაგირებს საკუთარი მშობელი კონტეინერის სიგანეზე, ვიუპორტისგან დამოუკიდებლად. 2025 წლის აგვისტოდან ეს თვისება Baseline Widely Available სტატუსშია — ანუ სრულად მხარდაჭერილია ყველა თანამედროვე ბრაუზერში (Chrome, Safari, Firefox, Edge), საიმედოდ გამოსაყენებელია production პროექტებშიც. 

/* 1. მშობელს ვუცხადებთ, რომ ის არის "container" */
.card-wrapper {
  container-type: inline-size; /* გვაინტერესებს სიგანეს (არა სიმაღლეს) */
  container-name: card-area;    /* არასავალდებულო, მაგრამ სასარგებლო სახელი */
}

/* 2. შვილი ელემენტი რეაგირებს container-ის (არა ვიუპორტის!) სიგანეზე */
@container card-area (min-width: 400px) {
  .card {
    display: flex; /* ფართო container-ში — გვერდიგვერდ */
  }
}

@container card-area (max-width: 399px) {
  .card {
    display: block; /* ვიწრო container-ში (მაგ. sidebar) — დაწყობილი */
  }
}

ეს ნიშნავს, რომ ერთი და იგივე .card კომპონენტი ავტომატურად „სწორად" გამოიყურება, სადაც არ უნდა ჩასვა ის — ვრცელ სექციაშიც და ვიწრო sidebar-შიც — HTML-ის ან media query-ების დუბლირების გარეშე. სწორედ ეს განასხვავებს მას media query-სგან: media query ეკუთვნის გვერდს, container query ეკუთვნის კომპონენტს.
